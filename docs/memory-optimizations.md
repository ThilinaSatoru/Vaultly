# Memory and activity reporting

SQLite uses a 32 MiB page-cache target, disk-backed temporary tables and no memory-mapped database pages. This bounds database cache growth, not the whole application's memory. Temporary work may incur additional disk I/O.

Attribute patterns are fetched only for requested IDs in batches of 500. Imports build matchers only for imported attributes rather than loading every attribute and filtering afterward. Closed attribute selectors do not build search results.

Attribute JSON uploads stream the file twice: the first pass validates JSON syntax, envelope metadata and individual record sizes without storing the dump; the second pass sends sequential chunks of at most 10,000 records and 20 MiB of UTF-8 JSON. Envelope metadata is preserved even when it follows the records array. Upload totals aggregate created/updated/indexed counts across chunks, and sidebar progress counts confirmed records. Each request is atomic, while the whole file is not: a schema or network error stops further requests and completed chunks remain committed. The attribute lists refresh after partial success. A single record too large for a request cannot be split and is rejected before uploads begin. Parsing periodically yields to keep the UI responsive.

Scanning avoids loading the previous index for marker normalization when no marked names exist. Reconciliation arrays are released before metadata and cover processing. Video signatures use indexed ID lookups. Cover dimension and directory caches are bounded by entry count. Comic alias matchers are built only when embedded comic metadata is encountered, and parsed metadata is discarded once assigned. Rescan-all refreshes the large frontend attribute lists after the final scan rather than once per completed source.

Book archive reads share the existing two-process resource limit. Archives larger than 32 MiB are not retained in the cache; smaller cached archives expire after 30 seconds. Backup restores inspect only the file header and send the original file rather than duplicating it as an ArrayBuffer and decoded text.

Scans already serialize source work regardless of which drives contain the sources. During a source scan, media subprocess concurrency now drops from two to one. Cover dimension inspection decodes images in short-lived child processes and waits for exit before releasing the resource slot, so decoded native image buffers cannot accumulate in the main process across sources. Unchanged covers reuse persisted dimensions after checking their file signature and candidate priority. First-time or changed artwork inspection incurs process startup overhead. The desktop build includes the cover worker. Image uploads still normalize artwork in the main process.

The sidebar combines server scan/conversion/thumbnail activity with local upload preparation, imports, backup exports and outstanding API mutations. Unknown progress remains indeterminate. Database connectivity follows the activity endpoint (which queries SQLite); processing status follows outstanding operations. API RSS is always shown in the expanded sidebar, along with system CPU and free memory. It excludes Electron renderer/GPU and child-process memory and must not be interpreted as total desktop memory.

Validation: API and web type checks; targeted import, 12k-attribute benchmark, cancellation, hash-marker reconciliation, resource-governor, archive and sidebar regression tests. The user's reported 8 GB desktop peak has not been reproduced, so no measured before/after memory reduction is claimed. Source discovery/reconciliation and backup export still retain library-sized structures; profile the workload causing the peak before replacing those pipelines.
